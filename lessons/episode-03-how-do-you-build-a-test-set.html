Episode 3 — How Do You Build a Test Set?

Episode 3 · Module 1 — Foundations: What a Number Means · Audio 6:40 · Statistics for Legal Evals

Audio

The legal department is about to pilot the contract platform from Episode 1. Before a single document is scored, one decision matters more than any formula in the rest of this series: which documents go into the test set. A biased test set makes every number after it meaningless. No formula fixes a test set that does not look like the work.

The question this episode answers: how do I know my test set is fair? The worked example is the platform’s pilot: a sampling frame of 50 contracts, chosen by type, with the prompt tuned on 30 of them and tested on the untouched 20.

First, Name the Population

A test set is a set of items used to measure how well a tool performs. The population is the full set of items the tool will actually be used on — in this case, the commercial agreements the department receives in its real work: NDAs, MSAs, software and SaaS agreements, vendor and procurement contracts, data protection agreements (DPAs), statements of work, and licensing and technology agreements. The test set is useful only to the extent that it resembles that population.

The sampling frame is the list the test set is actually drawn from. The frame is not the same thing as the population. A frame built from the department’s template library, for example, contains clean standard documents; the population contains bespoke vendor contracts with non-standard terms. A test set drawn from the template frame measures performance on templates, not on the department’s real work. The first check on any test set is therefore a check on its frame: does the list it was drawn from cover the population, or only the convenient part of it?

Three Ways to Choose: Random, Convenience, Stratified

Convenience sampling takes the items that are easiest to reach: the 50 contracts already on a shared drive, the ones a colleague happens to have to hand. Convenience sampling is fast, and it is the most common way a pilot test set gets built. Its weakness is that easy-to-reach items are rarely typical items. If the 50 easiest contracts are all template NDAs, the score says nothing about the bespoke vendor contracts the department actually receives. A convenience sample can still be used, but only if the report states plainly that it is a convenience sample and what it leaves out.

Random sampling gives every item in the frame the same chance of being chosen, for example by numbering the contracts in the frame and drawing numbers at random. Random sampling does not guarantee a representative sample in any single draw — a random draw of 50 can still come out light on MSAs by chance — but it removes the chooser’s preferences from the selection, and it makes the sampling error quantifiable. That is the subject of Episode 4.

Stratified sampling divides the frame into subgroups, called strata, and samples from each subgroup separately. In the pilot, the strata are the document types: NDAs, MSAs, SaaS agreements, DPAs, and vendor contracts. Stratification guarantees that each type appears in the test set in the intended proportion, which random sampling alone does not guarantee at small sizes. It also makes the subgroup scores reportable: the department can read the NDA score and the MSA score separately, which is what Episode 1 showed matters.

Oversampling, and Weighting Back

Some categories are rare but consequential. Indemnity-heavy MSAs are a small share of the department’s portfolio, but a missed indemnity clause in one of them is expensive. A test set that samples strictly in proportion to the portfolio might contain only one or two of them — too few to learn anything about performance on that category.

The remedy is oversampling: deliberately include more of the rare category than its portfolio share, so there are enough of them to measure. Oversampling is legitimate, but only if the results are then weighted back to the portfolio mix. Weighting back means each subgroup’s score is multiplied by its share of the real portfolio, not its share of the test set, before the subgroups are combined into an overall score. The arithmetic is the same as the portfolio weighting in Episode 1: a weighted mean, where the weights are the portfolio shares. An overall score computed from an oversampled test set without weighting back describes the test set, not the portfolio. The weights must be stated alongside the score, so a reader can see what mix the headline number was computed over.

The same logic applies in reverse. If a category is over-represented in the test set for any reason — because it was oversampled, or because it was simply easier to collect — the unweighted overall score overstates that category’s importance. The fix is the same: weight back to the population the decision is about.

The Worked Example: 50 Contracts, Split 30 and 20

The pilot’s sampling frame is 50 contracts, stratified by type, with indemnity-heavy MSAs oversampled and the results weighted back to the portfolio mix. The 50 contracts are then divided into two groups with different jobs:

  • Development set, 30 contracts. The prompt — the instructions given to the platform — was tuned on these 30 contracts. The team tried wording, checked the outputs, and adjusted the prompt until the outputs looked right on these contracts.
  • Evaluation set, 20 contracts. These 20 were untouched during tuning. They are the test: the platform, with its final prompt, is run on them once, and the score is the score on these 20.

The split is the point. The 30 development contracts cannot also be the test, because the prompt was adjusted until it performed well on them. A score on the development set measures how well the tuning worked, not how well the platform will perform on new contracts. Testing on the same contracts used for tuning overstates performance, and the overstatement is invisible in the score itself — nothing in the number says it was computed on tuned-on data. The only protection is the separation: development data and evaluation data must be different contracts, and the evaluation contracts must stay untouched until the test runs.

The same separation applies to people as well as prompts. If a lawyer reviewed the development contracts and learned the platform’s failure patterns from them, that knowledge can leak into the grading of the evaluation contracts. The evaluation grading should be done against the same rubric, by graders who did not tune the prompt.

Leakage and Contamination

Leakage is information from the test reaching the thing being tested before the test runs. The development split above is one form of leakage: tuning on the test data. Contamination is a related problem at the level of the model itself: if the platform’s training data included the benchmark cases, or documents very like them, the score is inflated. The platform is not performing well on new work; it is remembering work it has already seen.

Contamination is difficult to detect from the score alone, because a contaminated score looks like a good score. The questions to ask are about provenance: what was the model trained on, and does the training data overlap with the test set? Where the training data cannot be inspected, a clean test set — documents created after the model’s training cut-off, or documents written specifically for the test — is the practical protection. A vendor that cannot say what its model was trained on cannot rule contamination out, and the report should say so.

Label Noise: Two Lawyers Disagreed on 8 of 50

The reference labels are the scores the lawyers assigned to each contract: the standard against which the platform is measured. In the pilot, two lawyers independently scored the same 50 contracts, and they disagreed on 8 of the 50 scores. That is a disagreement rate of 8 ÷ 50 = 16%. The disagreement is label noise: uncertainty in the reference labels themselves.

Disagreement on 8 of 50 does not mean the labels are useless. It means the labels need investigation before they are used as a standard. The team should investigate whether the disagreements reflect unclear grading instructions, rater error, missing information, or genuine legal ambiguity. Each cause points to a different fix:

  • Unclear grading instructions: rewrite the rubric so the two lawyers are applying the same standard.
  • Rater error: one lawyer misread a clause or misapplied the rubric; the score can be corrected.
  • Missing information: the contract as provided did not contain what the grader needed; the test item needs completing, not the grader.
  • Genuine legal ambiguity: two competent lawyers can reasonably differ on the point. The label is genuinely uncertain.

Where a disagreement can be resolved, refine or adjudicate the reference labels: the two lawyers discuss the item, or a third lawyer decides, and the agreed label is recorded. Where it cannot be resolved, report the unresolved uncertainty alongside the score, rather than picking one lawyer’s label and treating it as certain. Reference labels require validation: a label is a claim about the right answer, and it needs the same scrutiny as the platform’s output.

Rater disagreement sets a rough ceiling on how closely any output can match one lawyer’s label. If two lawyers agree on only 42 of 50 scores, no system can match a single lawyer’s labels on all 50, because the labels themselves disagree. That ceiling applies to matching one lawyer’s label. It does not cap a model against an adjudicated reference — a label the lawyers agreed after discussion — and it is not a universal performance ceiling. The distinction matters: the ceiling is a property of the labels, not of the task. Episode 15 takes up agreement between graders in full, including Cohen’s κ.

The Unit of Evaluation

The unit of evaluation is the thing being scored: one item, one score. The pilot’s unit is the document: each contract receives one score out of ten. But the unit could equally be a clause, a question, a proposition, a citation, or a run. The choice of unit changes what the score means.

A platform that scores 9 out of 10 at the document level can still miss the one clause that matters. A platform that extracts 95% of clauses correctly can still fail every document that contains an indemnity clause, if the missed clauses cluster in those documents. The unit should match the decision: if the decision is whether the platform can be trusted to review a contract, the unit is the document. If the decision is whether it extracts clauses reliably, the unit is the clause. Report the unit alongside the score, and check that the unit in the vendor’s report matches the unit in your decision. Episode 13 returns to this point from a different direction: items drawn from the same document are not independent items.

Three Levels of Evaluation

An evaluation can be run at three levels, and the level should be stated:

  • Model evaluation: does the underlying model extract clauses correctly? This tests the model in isolation, on a fixed task, with everything else held constant.
  • Product evaluation: does the complete tool work — the retrieval, the prompts, the document handling, the interface? A good model inside a poor product still produces poor results for the user, and a product test is what measures that.
  • Workflow evaluation: does a lawyer using the tool do better work than a lawyer without it? This is the level the department’s decision is really about. It is also the hardest to run, because it needs lawyers doing real work with and without the tool, and measuring the difference. Episode 19 takes up workflow evaluation in full.

A model score is not a product score, and a product score is not a workflow score. Each level answers a different question, and a report should say which level it tested.

The Evaluation-Design Worksheet

The practical output of this episode is a worksheet, completed before any results are examined. It records the decisions that make a test set defensible:

  • Intended user, workflow, jurisdiction, and legal date: who will use the tool, for what work, under which law, as at what date?
  • Unit of evaluation: matter, document, question, proposition, citation, or run?
  • Target workload and legally meaningful subgroups: which document types, which clauses, which risk levels?
  • Representative testing or deliberately difficult “challenge” testing: is the set meant to resemble the ordinary workload, or to stress the tool on hard cases? Either is legitimate, but a challenge set must be labelled as one, and its score must not be reported as if it were a representative score.
  • Separation of development examples from untouched evaluation data: which items were used for tuning, and which were held back?
  • Definition of success, consequential failure, and acceptable uncertainty: what score counts as good enough, which failures matter most, and how much uncertainty is acceptable?

The worksheet is completed before any results are examined, because decisions made after seeing the results are easy to tilt, even unintentionally, toward the result that looks best. Deciding the tests before looking is the subject of Episode 18.

The Use Case: Judging a Vendor’s Test Set

A vendor reports a score of 92% on its own test set. The questions from this episode are: what was the sampling frame, and did it cover the department’s real work or only the vendor’s template library? Was the set stratified by document type, and were rare but consequential categories oversampled and weighted back? Was the test set separate from the data used to develop the tool, or was the tool tuned on the same items it is now being scored on? Were the reference labels validated, and how often did the graders disagree? What is the unit of evaluation, and does it match the decision the department is making? A vendor that can answer those questions has a test set worth reading. A vendor that cannot has a number, not an evaluation.

Checklist: Building a Test Set

  • Name the population before choosing the frame, and check the frame covers it.
  • Stratify by the subgroups that matter, and report the scores by subgroup.
  • Oversample rare but consequential categories, and weight the results back to the portfolio mix.
  • Split development from evaluation, and keep the evaluation set untouched until the test runs.
  • Ask what the model was trained on, and whether the test set overlaps with it.
  • Investigate grader disagreement, adjudicate where possible, and report unresolved uncertainty.
  • State the unit of evaluation and the level of evaluation, and check they match the decision.
  • Complete the evaluation-design worksheet before examining any results.

Conclusion

More examples cannot repair an unrepresentative test set. Teach sample quality alongside sample size. A test set of 50 well-chosen contracts, stratified by type, split between development and evaluation, and graded against validated labels, tells the department more than a test set of 500 convenience documents.
